# SECURITY.md — безопасность tinydb

## Threat model

Сервер защищает данные **at-rest**: снятый с устройства диск/бэкап/снапшот
(`db.sqlite.enc`, `backup`) без ключа нечитаем. Ключ — 256 бит энтропии.

Что **не** покрывается:

- атакующий с выполнением кода в процессе/на устройстве при живом сервере —
  plaintext `db.sqlite` и ключ (`db.key`) лежат в `-data` и доступны ему;
- атакующий, читающий память процесса (shell/root);
- TLS: трафик между клиентом и сервером — обычный HTTP на loopback.
  Сеть не шифруется — только данные на диске. Выносить API наружу нужно
  через stunnel/Tailscale/ssh-tunnel.

То есть модель узкая и честная: **at-rest шифрование по умолчанию**, без
претензий на защиту от компрометации живой машины.

## Формат контейнера WEBDBENC

Стримовое AES-256-GCM, реализация — `internal/cryptobox`.

```
offset  size  поле
0       8     "WEBDBENC"          — магический заголовок
8       1     версия формата (1)
9       1     флаги
10      8     размер plaintext, big-endian
18      12    nonce первого чанка
...           чанки по 64 КиБ plaintext:
              nonce(12) | ciphertext(N) | tag(16)
```

- Ключ: AES-256 (32 байта).
- Каждый чанк — отдельный nonce, GCM-тег (128 бит) проверяется на чтении:
  битый/подменённый чанк → ошибка расшифровки, не тихая порча.
- AAD (дополнительные ассоциированные данные) — заголовок контейнера
  (магия, версия, размер). Подмена метаданных ломает тег первого чанка.
- `struct streaming` позволяет шифровать файл, не держа его в памяти целиком
  (важно для RAM-лимита 10 МБ): читаем 64 КиБ → шифруем → пишем.

Порядок записи снапшота: `.<name>.tmp` → `fsync` → `rename` поверх
`db.sqlite.enc` → `fsync` каталога. Атомарно: либо старый снапшот, либо
новый, обрезанного «полуфайла» не бывает. Мусорный `.tmp` при старте
удаляется.

## Ключи

Два взаимоисключающих режима (`-key-file` против `-passphrase*`):

### 1. Keyfile (по умолчанию)

`data/db.key` — 32 сырых байта, создаётся при первом старте с правами
`0600` (каталог `0700`). Ничего не выводится в лог. Утеря ключа =
утеря данных безвозвратно (по умолчанию). Копируйте `db.key` вместе с
`db.sqlite.enc`.

### 2. Пароль (passphrase)

`-passphrase`, `-passphrase-file` или env `WEBDB_PASSPHRASE`
(предпочтительнее — не виден в `ps`).

Из пароля ключ выводится KDF:

```
key = PBKDF2-HMAC-SHA256(password, salt, 100000 итераций, 32 байта)
```

- соль генерируется криптостойко и лежит в контейнере;
- 100k итераций — на сколько хватает терпения embedded-устройству;
  перебор словаря на устройстве остаётся дорогим;
- смена пароля = перешифровать снапшот заново (экспорт/импорт).

PBKDF2 выбран вместо Argon2 из-за размера/зависимостей: в библиотеке
только stdlib `crypto/*`, лишних мегабайт text не появляется.

## Права и изоляция

- `data/` — `0700`, `db.sqlite`, `db.sqlite.enc`, `db.key`, `token` — `0600`.
- Plaintext на диске живёт **только пока жив процесс** (и то не всегда:
  по умолчанию после завершения он удаляется, остаётся `.enc`;
  `-keep-plain=true` — осознанное послабление для отладки).
- `GET /v1/backup` отдаёт уже зашифрованный снапшот, plaintext по сети
  не ходит никогда.

## Аутентификация API

- Токен: 32 байта, hex (64 символа), генерируется при первом старте в
  `<data>/token` (`0600`). Задаётся флагами `-token`/`-token-file` или
  env `WEBDB_TOKEN`.
- Проверка: `Authorization: Bearer <token>` или `X-API-Key: <token>`,
  сравнение без короткого замыкания по времени на уровне приложения.
- `GET /health` открыт (нужен для лайвнес-чеков), всё `/v1/*` закрыто.
- `-no-auth` — только локальная разработка; документировано в help.
- Токен не логируется.

## Дополнительно

- **Ограничение тела запроса** `-max-body` (4 МиБ) — защита RAM от
  заброса гигабайт; `/v1/import` стримится и ограничен отдельно,
  `-max-import` (64 МиБ) — иначе лимит нельзя соблюсти, не буферизуя
  поток в памяти. Превышение → `413`, транзакция откатывается.
- **Квота 100 МБ** (`PRAGMA max_page_count`) — защита диска: переполнение
  → понятная ошибка, файл не растёт бесконечно.
- **SQL только на чтение** — инъекции, ведущие к записи/разрушению схемы,
  недоступны; аргументы передаются параметризованно (`?`).
- **Имена коллекций/полей** валидируются вручную (без regexp): допустимы
  `A-Za-z0-9_-`, длина до 64, префикс `_` у коллекций зарезервирован за
  системными таблицами (`_collections`, `_meta`) и отклоняется —
  SQL-идентификаторы для индексов конструируются только из проверенных
  имён (экранирование `"`/`''` не требуется, имена не проходят в сыром виде).
- **Все перечисленные проверки закреплены автоматикой**: `tests/security.sh`
  (auth, инъекции SQL, валидации, лимиты, права файлов, tamper/wrong-key,
  отсутствие токена в логах, CORS) — входит в `make test` и CI.
- **CORS выключен по умолчанию** (`-cors` — явное включение): браузерный
  доступ из произвольного origin к локальной БД — не сценарий по умолчанию.
- **Ре-exec без `LD_PRELOAD`** (см. DESIGN.md): в окружение потомка не
  передаётся сторонний код, подсовываемый окружением Termux.

## Резюме по рискам

| Угроза | Статус |
|---|---|
| Чтение диска/бэкапа без ключа | защищено (AES-256-GCM + tag) |
| Подмена чанка/заголовка | защищено (GCM-tag, AAD) |
| Подбор passphrase | PBKDF2 100k; слабый пароль — слабая защита |
| HTTP без токена | 401 на всё `/v1/*` |
| Запрос-бомба | `-max-body`, `-max-import`, квота 100 МБ, буфер write-back ограничен |
| Компрометация живого процесса/устройства | **вне модели** |
| Перехват loopback-трафика | **вне модели** (нет TLS) |
